# Blender and Unreal animation handoffs

Kimodo generates a skeletal performance. Blender imports the performance and exports an FBX animation. Unreal imports that FBX onto a compatible, existing character skeleton. Applying SOMA motion to a different character rig requires a separate retargeting step; sharing a humanoid appearance does not make two rigs compatible.

## Blender

Prepare a handoff from a completed SOMA BVH artifact. The server takes timing and checksum data from the job manifest and writes a fixed Python script beside `handoff.json` in its managed data directory. Preparing the handoff does not execute Blender or alter a scene. An existing Blender MCP connection can execute the exact returned script using Python's `runpy.run_path(script_path, run_name="__main__")`. `script_path` is the returned local path, passed as a string value.

`prepare_blender_handoff` uses the original manifest-listed BVH when `export_id` is omitted. If a completed SOMA job has only native NPZ, call `export_motion` with `format="bvh"` first, then pass its returned 64-character `export_id` to preparation. This selects a verified derived BVH through its receipt; it does not accept a filesystem path or replace the original manifest. The prepared result identifies `source_export_id` and `export_options`. Choose `bvh_standard_tpose` explicitly when converting: standalone export defaults to the BONES-SEED rest pose, while natural-brief generation requests standard T-pose BVH.

Conversion preserves source timing and runs without inference or downloads, using the installed runtime and canonical skeleton assets. Identical source/options reuse a reverified export receipt; incomplete conversion attempts remain for operator inspection. Only BVH feeds this SOMA handoff; AMASS and CSV are separate interchange exports. See [completed-motion export](agent-workflows.md#export-existing-motion-without-inference) for format options and representation caveats.

Keep `sample_index` and `attempt` identical when preparing, executing, and reading the skeleton report, and pass `source_kind="skeleton"` explicitly to execution/report tools. The `attempt` identifies an editor handoff independently of the conversion's `export_id`. An occupied attempt with different source data is not overwritten; inspect it before choosing an unused attempt. Verified output discovery and downloads bind the original NPZ manifest, derived BVH receipt, and subsequent skeleton receipt together.

For execution from the studio or Kimodo's own MCP tools, call `execute_blender_handoff` with the same job, sample, attempt, and source kind used during preparation. This integration was checked with [Blender Lab's MCP extension](https://www.blender.org/lab/mcp-server/) version 1.0.3. Its bundled installation guide directs users to add `https://lab.blender.org/` as a Blender Extensions repository, then install and enable the MCP addon. The companion MCP server is maintained in [Blender Lab's repository](https://projects.blender.org/lab/blender_mcp). Install those components separately; they are not bundled with this bridge.

The compatible addon must listen on `127.0.0.1:9876`: this bridge uses its null-terminated JSON `execute` protocol with `strict_json=true`. A different addon called “Blender MCP” may use another protocol and is not automatically compatible. The separate assistant-facing Blender MCP connection remains useful for inspecting scenes and performing deliberate manual refinement.

Before dispatch, the bridge verifies the bundled script, prepared request, and source checksums. It serializes managed exports, records a dispatch receipt before sending, and validates the resulting hierarchy, timing, and output checksums. A completed, matching receipt is reused. After an uncertain timeout or connection failure, inspect the report and Blender before choosing another attempt; automatic resubmission could duplicate work. The studio's **Build character preview** action performs preparation and checked execution together for the registered character.

The script checks the BVH checksum and requires unused output filenames. It creates a separate scene, imports at a scale of 0.01 because Kimodo BVH stores centimeters, and preserves the canonical 30 FPS frame count. Kimodo's Y-up, +Z-forward coordinates are converted to Blender coordinates by the BVH importer. The imported armature is named `KimodoRig`, avoiding Unreal's special handling of an object named `Armature`.

Only that armature is exported. FBX settings use -Y forward, Z up, no generated leaf bones, one sample per frame, no key simplification, and the active action only. NLA strips and unrelated actions are excluded. The scene is saved independently with `bpy.data.libraries.write`, so the currently open project's filename is not replaced and unrelated scenes are excluded. The previously active scene is restored afterward.

Outputs are `animation.blend`, `animation.fbx`, and `blender-report.json`. The report records the Blender version, frame range, sample rate, bone hierarchy, and artifact checksums. The FBX hierarchy includes its explicit `KimodoRig` armature node in addition to the BVH's `Root` wrapper and SOMA bones. A 77-joint SOMA skeleton therefore produces 78 imported BVH bones; the FBX hierarchy includes one further armature node.

The script refuses an existing `KimodoRig` object, a non-Object editor mode, changed source data, or existing output files. Use a fresh session when another Kimodo armature is already loaded. Repeating preparation with the same inputs returns the same files; executing twice does not overwrite earlier exports. A failed execution may leave partial exports and its reservation marker; prepare a new directory after reviewing the error.

The operator signatures and selective scene-writing API were checked in installed Blender 5.2.1. [Blender BVH documentation](https://docs.blender.org/manual/en/latest/addons/import_export/anim_bvh.html) explains axis conversion and frame-rate handling; [Blender FBX documentation](https://docs.blender.org/manual/en/latest/addons/import_export/scene_fbx.html) describes the exporter and its armature limitations. Compatibility with another Blender release must be checked by that editor before export.

The complete export was checked with an upstream 150-frame reference motion at 30 FPS. Reopening the saved blend file showed only the intended scene and armature. Importing the exported FBX back into Blender preserved all 78 bone names and frames 1..150; the largest joint-position difference across five sampled frames was 0.0000182 meters. Use `anim_offset=0.0` for that verification: Blender's default FBX import offset shifts the animation by one frame. This verifies file conversion on a reference motion, not new model inference or retargeting to a custom character.

Comparing the original 30-joint NPZ with the exported BVH over all 150 frames gave a maximum 0.0000042-meter difference for 26 body joints. The four hand endpoints differed by approximately 0.023–0.060 meters because upstream's conversion to the 77-joint skeleton inserts relaxed hand poses. Detailed fingers are synthesized by that skeleton expansion rather than independently generated, so exact reduced-skeleton hand endpoint preservation is not guaranteed.

## Unreal

An Unreal handoff requires a successful Blender export report, an absolute `.uproject` path, an existing Skeleton content path, its SkeletalMesh content path, a destination directory under `/Game`, and a new animation asset name. These are explicit project decisions. The bridge never guesses a project from another open editor or writes into an arbitrary default character folder.

Enable `PythonScriptPlugin` in the intended project and enable its Python Remote Execution setting with multicast bind address `127.0.0.1` and multicast TTL `0`. Register the installed engine root through `KIMODO_UNREAL_ENGINE`, or create `Unreal/engine.json` beneath `KIMODO_DATA_DIR`:

```json
{"engine_directory": "D:/Tools/UE_5.8"}
```

Use the installation directory containing `Engine`, not the `Engine` directory itself. Engine configuration belongs to the local operator; MCP tool arguments cannot supply executable paths or Python code. For a separate validation project, `python scripts/create_unreal_project.py --directory "D:\AnimationLab"` creates a new project with the required plugins and loopback settings. It refuses existing directories and does not launch the editor.

The installed Unreal 5.8 native MCP server is enabled with the `ModelContextProtocol`, `EditorToolset`, and `AnimationAssistantToolset` plugins. Launch the intended editor with `-ModelContextProtocolStartServer -ModelContextProtocolPort=8000` to expose `http://127.0.0.1:8000/mcp`. Discover its `list_toolsets`, `describe_toolset`, and `call_tool` schemas before use. In the tested release, `SkeletalMeshTools.import_file` can import the initial skinned character mesh; it has no animation-only import tool. The bridge's execution tool uses the engine's supported Python transport for that step.

Call `prepare_unreal_handoff`, then `execute_unreal_handoff` with the same job, target, source kind, sample index, and attempt. For a fitted character, use `source_kind="character"`. Execution verifies the prepared script against the bundled template, discovers exactly one editor matching both the project and configured engine, and serializes commands through loopback port 6776. The editor stays open between clips. A matching completed receipt is reused without importing again. If execution times out, inspect `get_unreal_report` before retrying because the editor may still have finished the import.

The script first checks the open project, input hashes, and unused destination. It loads the requested rig and uses a transient, unattached SkeletalMeshComponent to compare every bone name and parent with the source FBX hierarchy. It also checks that the mesh uses the requested Skeleton. A mismatch stops before asset import. These checks establish hierarchy compatibility; they do not prove that two independently created rigs share identical rest transforms or proportions. Use a skeleton created for the same exported rig, or first retarget and validate a new export on the intended character.

Import uses [AssetImportTask](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/AssetImportTask?application_version=5.6) and an explicit legacy FBX factory. [FbxImportUI](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/FbxImportUI?application_version=5.6) is configured for animation only, with automatic type detection disabled and the existing skeleton assigned. Materials, textures, meshes, physics assets, and replacement of existing assets are disabled. [FbxAnimSequenceImportData](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/FbxAnimSequenceImportData?application_version=5.6) preserves the exported range and 30 FPS sampling.

The new animation is saved only after the returned asset type, path, skeleton, timing, and bone tracks match the request. Unreal counts the intervals between animation samples separately: an inclusive Blender range of 1..150 contains 150 sampled keys and normally 149 frame intervals. The report records both counts and playback duration rather than conflating them. Its metrics come from the [animation data model](https://dev.epicgames.com/documentation/en-us/unreal-engine/python-api/class/AnimDataModel?application_version=5.6). The script reads the current `data_model_interface` property, with a legacy fallback, and compares track names using Unreal's case-insensitive name semantics while rejecting collisions and missing tracks.

Unsupported editor APIs or changed import behavior cause a failure instead of falling back to editor defaults. An import failure may leave a new unsaved asset in the editor; this script does not delete editor assets automatically. The integration does not save maps or replace skeleton assets. A failed execution leaves its reservation marker for diagnosis; choose a new destination or attempt after reviewing the failure rather than overwriting it.

The complete managed workflow was executed in Unreal 5.8.3 against a separate validation project, using a newly generated waving motion on the registered character. `prepare_unreal_handoff`, `execute_unreal_handoff`, and `get_unreal_report` completed through MCP, producing `/Game/Kimodo/Animations/AnimeGirl_Wave.AnimeGirl_Wave`. The receipt confirms the matching character Skeleton, 24 bones and 24 animation tracks, 120 sampled keys, 119 frame intervals, 30 FPS, and 3.966667 seconds between the first and last keys. Native Unreal MCP separately confirmed the imported character's 99.951-centimeter height and the saved animation data. Root-motion extraction was left at Unreal's default disabled setting. These checks establish asset, hierarchy, unit, and timing correctness; they do not establish rendered or gameplay acceptance.

## Character retargeting

`get_character_profile` describes the registered, inspected source asset. `prepare_character_handoff` supports its specific 24-bone fitted rig: the original static FBX is preserved while a separate armature, vertex weights, and retargeted SOMA animation are created. Its helper verifies the original asset checksum and the completed motion artifact. It does not perform arbitrary character recognition or automatically fit unrelated meshes.

The managed outputs are `character.blend`, a rest-pose skeletal mesh `character.fbx`, an animation-only `animation.fbx`, `character-preview.glb`, and `blender-report.json` with timing, hierarchy, hashes, and deformation diagnostics. The GLB contains its textures, skin, and sampled animation for interactive browser playback. The studio checks that each preview belongs to its selected job and sample, then exposes the latest validated attempt and its downloads. Import the skeletal mesh first, then use its actual Skeleton and SkeletalMesh paths for `prepare_unreal_handoff` with `source_kind="character"`. `get_handoff_report` and `get_unreal_report` expose the separate editor results.

This character export bakes centimeters into FBX coordinates with `FBX_SCALE_NONE`, and names the armature object `Armature` so Unreal removes that wrapper and retains the fitted `Root` as the first bone. This differs intentionally from the generic SOMA skeleton export described above. The report supplies the resulting 24-bone hierarchy for the compatibility check. Preserving the wrapper, using a mesh imported at another scale, or assigning a different Skeleton makes the export unsuitable for that target.

The fitted profile has no facial or independent finger animation, and no simulated cloth or hair. Weights and body proportions are specific to the inspected character. Numerical checks establish finite transforms, normalized skin weights, and preserved bone lengths; they do not prove that every pose is visually suitable.

For Manny, MetaHuman, Mixamo, or a custom rig, first establish a source rig, a target rig, reference poses, scale, root-motion policy, and bone/chain mapping. An Unreal IK Rig/IK Retargeter workflow or a verified Blender retargeting workflow can then bake motion onto the target. Exporting the original SOMA animation under a new filename or assigning an unrelated Skeleton does not perform retargeting. Preserve the original mesh, textures, rig, and source animation while producing separate retargeted outputs.

## Execution boundary

The MCP bridge prepares fixed scripts and can execute its verified Blender handoff through the compatible local addon and its Unreal handoff through the installed engine's Python transport. It has no tool that accepts arbitrary Python, shell commands, or editor expressions. Variable data lives in JSON, and the executable script is checked before dispatch and again inside Unreal. Native Unreal MCP remains available for asset import and inspection; its programmatic tool restrictions are not altered. Both editors and their local connections remain under the operator's control. Prepared output files, model caches, and machine-specific configuration belong outside the Git repository.
